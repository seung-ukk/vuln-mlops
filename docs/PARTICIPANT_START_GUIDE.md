# ModelGate 참가자 안내

## 이 랩에서 살펴볼 신뢰 경계

외부에서 접속하는 MLOps 서비스가 모델을 자동 검증한다. 이 실습의 초기 서비스는
MLflow 모델 역직렬화 취약 구성을 의도적으로 사용한다. 모델 데이터가 검증
프로세스에서 실행되면 참가자는 제한된 validator Pod의 문맥을 조사할 수 있다.
그 뒤 내부 모니터링, 운영 로그, 제한된 Git 쓰기 권한과 Argo CD를 따라가며
전용 maintenance 노드의 hostPath가 어떤 영향을 주는지 확인한다. 마지막
영향은 전용 EC2 노드의 실습용 증명 태그 변경이다.

목표는 각 이동에서 **누가 어떤 권한으로 실행됐는지**를 증명하는 것이다.
중간 Flag나 공개 `next` API는 현재 실습 경로에 없다.

## 시작 환경

- 공개 주소: **http://3.35.2.114/docs**. `/readyz`가
  `{"status":"ready"}`를 반환하면 접속이 허용된 상태다.
- 운영자가 별도로 전달하는 공격자 EC2에 SSH로 접속한다. 그 EC2는 같은
  VPC에 있으며 validator의 역방향 연결을 받는다. 참가자에게 EC2의 접속
  방법과 수신용 사설 IP가 전달된다. 참가자는 EC2에서 사용 가능한 TCP
  리스너 포트를 직접 고를 수 있다. 비루트 계정이라면 1024–65535 범위를
  사용한다. EC2에는 EKS 운영자 권한이나 AWS 역할이 없다.
- 공개 API에는 모델 ZIP 업로드, 등록, 검증 Job 조회가 있다. 정상 MLflow
  모델도 이 경로로 검증된다. 정상 모델과 역직렬화 payload의 HTTP Job 결과가
  모두 `succeeded`일 수 있다. RCE 증거는 Job 상태 문자열이 아니라
  validator에서 시작된 실제 연결과 그 셸의 실행 문맥이다.
- 실습용 데이터만 사용한다. 개인 비밀번호와 업무 데이터를 업로드하지 않는다.

## 조사 흐름

1. 공개 화면과 `/docs`에서 모델 bundle 형식, 자동 검증 흐름, Job 응답을
   확인한다. 이 랩에서는 취약한 MLflow 역직렬화가 초기 진입점이라는
   전제가 제공된다. 구체적인 payload는 참가자가 구성한다.
2. validator 셸을 얻었다면 현재 디렉터리와 운영 메모를 살핀다. 내부 DNS,
   Grafana datasource와 보관된 운영 점검 기록이 다음 조사 방향을 제공한다.
   셸에는 제한된 ServiceAccount와 `kubectl`이 준비돼 있다. 운영자
   kubeconfig는 제공되지 않는다.
3. 발견한 Git credential은 로그에 지정된 저장소·브랜치·경로에만 사용한다.
   저장소의 운영 문서와 Deployment를 읽고, Git commit과 Argo CD가 반영한
   revision을 비교한다.
4. 전용 maintenance 노드에서 컨테이너의 UID, mount의 읽기 전용 설정,
   호스트에서 실행되는 작업 사이의 관계를 확인한다. 참가자가 볼 수 있는
   내부 Pod 로그와 Git revision을 증거로 남긴다. 실제 EC2 태그와 CloudTrail
   호출자 대조는 운영자가 수행한다. 로그의 문구만으로 AWS 성공을 단정하지
   않는다.

팀원은 공유 Git 브랜치와 전용 노드를 순서대로 사용한다. 한 명의 실습이
끝나면 운영자가 baseline과 노드를 초기화한 뒤 다음 참가자가 시작한다.
